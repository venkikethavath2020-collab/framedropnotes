# Interview Q&A — Upload Flow

---

## Q1: Why did you use a 3-step sign/upload/finalize flow instead of proxying uploads through your backend?

**Beginner answer:**
I didn't want large image files going through my Node.js server. It would slow things down and use too much server memory. By having the browser upload directly to R2, the backend only handles metadata.

**Mid-level answer:**
If I proxied uploads through Node.js, every concurrent upload would tie up memory and an open TCP connection for the entire upload duration — potentially minutes for large files. Cloudflare R2 supports presigned PUT URLs via the S3-compatible API. The backend generates a short-lived presigned URL (a fast operation), the browser streams the file directly to R2, and then the backend records the result in PostgreSQL. This separates the stateless signing concern from the stateful storage concern.

**Senior answer:**
Three reasons this is the right architecture:
1. **Bandwidth cost** — backend egress doesn't scale with upload volume. R2 handles it at the edge.
2. **Reliability** — if the backend restarts mid-upload, the upload is lost. R2's infrastructure handles the connection independently.
3. **Node.js event loop** — Node is single-threaded. A 500 MB upload would block I/O processing even with streaming unless you're very careful with backpressure. Presigned URLs remove this risk entirely.

The `storage_key` prefix validation in finalize is the critical security control — it ensures a photographer can only register files they actually uploaded to their own R2 folder, not claim someone else's file by guessing a key.

**Architect answer:**
The sign/upload/finalize split is also an abstraction boundary. Today R2 is the storage backend — tomorrow it could be S3 or GCS. The `sign` step is where you swap the presigned URL logic, and `finalize` validation adapts — the upload pipeline (engine.ts, IndexedDB, Web Worker) stays unchanged.

One gap worth noting: there's no R2-side webhook to confirm upload success. The system relies on the browser calling finalize, which means a malicious client could skip finalize and leave orphaned R2 objects. We handle this with the weekly `r2OrphanReaper` worker, but a webhook-driven finalize would be more reliable at scale.

---

### Interviewer follow-ups

**"Why not use presigned POST instead of presigned PUT?"**
> S3-compatible presigned PUT is simpler — one URL, one request, browser streams binary directly. Presigned POST requires a multipart form and additional policy fields. PUT is less error-prone for our use case.

**"What happens if the browser uploads to R2 but never calls finalize?"**
> The file sits in R2 as an orphan. The `r2OrphanReaper` worker runs weekly, lists R2 objects, cross-references against the `photos` table, and deletes anything not recorded in the DB. We also have `r2Reconciliation` which samples R2 objects and alerts if the miss rate exceeds 0.1%.

**"What happens if finalize fails after the R2 upload succeeds?"**
> The file is in R2 but no `photos` row exists. The album photo count doesn't change. The reaper will clean it up within a week. On the frontend, the upload engine in IndexedDB marks the file as `finalizing` — if finalize fails, the job can be retried and the engine skips re-uploading to R2 if it already has the `storage_key` cached (resume optimisation).

**"How do you prevent someone from uploading to another photographer's album?"**
> The `storage_key` is generated by the backend during `sign` with a path like `users/{userId}/albums/{albumId}/{uuid}.jpg`. Finalize checks that the submitted `storage_key` starts with `users/{req.userId}/`. A different photographer cannot claim a key outside their own prefix.

**"How does the bulk upload work?"**
> Bulk upload (up to 500 photos) uses a 3-way pipeline: while batch N is being uploaded to R2, the backend is signing batch N+1, and finalizing batch N-1. Concurrency inside each batch is 15 parallel uploads. The whole job is persisted to IndexedDB so if the user navigates away and comes back, the upload resumes from where it left off.

## Q2: Why did you use a Web Worker for compression?

**Beginner answer:**
Compressing images on the main thread would freeze the UI. A Web Worker runs in a separate thread so the page stays responsive.

**Mid-level answer:**
Image compression using `OffscreenCanvas` is CPU-intensive. Running it on the main thread blocks the JavaScript event loop, causing the UI to stutter or freeze. The compression worker uses `OffscreenCanvas` + `canvas.convertToBlob()` — these are available in worker context. We run a pool of workers equal to `navigator.hardwareConcurrency || 4` to use all available CPU cores.

**Senior answer:**
The worker pool size matches hardware concurrency — this is important because more workers than CPU cores causes context-switch overhead. The compression parameters (1048px max, JPEG 0.85) were tuned to balance file size reduction against quality. At these settings, a typical 8MP DSLR photo compresses from ~6 MB to ~400–600 KB, which directly reduces R2 egress cost and gallery load times. The quality floor of 0.85 is important for photographers — they need to see detail in previews without downloading originals.

In the new upload engine (`services/upload/engine.ts`), the worker pool is a module singleton that survives Vue Router navigation. In the legacy composables, the pool is view-scoped and gets terminated when the component unmounts — which was a bug if the user navigated away mid-compression.

**Architect answer:**
The Web Worker approach has a limitation: `OffscreenCanvas` isn't available in all environments (older iOS WebKit had gaps). A more robust approach would be to use a WebAssembly-based codec like `@squoosh/lib` or `libvips-wasm` for consistent cross-platform compression with better quality/size trade-offs. For a photographer platform where print quality matters, lossless WebP as the upload format with lossy JPEG only for thumbnails would be worth evaluating.

---

### Interviewer follow-ups

**"What is the compression ratio you're targeting?"**
> Target is under 1 MB per image for upload — reduces R2 PUT cost and upload time on mobile networks. At 1048px, JPEG 0.85, typical results are 300–700 KB.

**"Why 1048px max dimension specifically?"**
> Tuned for gallery preview use case — enough resolution for a full-screen monitor view (1080p), not the original full-resolution file. The original is not needed for the sharing/selection use case. If we offered print-quality downloads, we'd store originals separately.

**"How would you handle a user uploading a 100 MB RAW file?"**
> Currently we compress JPEG files. RAW files (CR2, ARW, NEF) would need a different path — either reject them with a clear error, or use a server-side conversion pipeline (upload to R2, trigger a worker to convert RAW → JPEG, store result). We don't support RAW currently; photographers export JPEG from Lightroom before uploading.

## Q3: What is the IndexedDB upload resume mechanism?

**Mid-level answer:**
When the user starts an upload, the engine saves job and file records to IndexedDB (the `framedrops-uploads` database). Each file has a state: `pending → compressing → ready → signing → uploading → finalizing → done`. If the user refreshes or navigates away, on next boot the engine reads IndexedDB and resumes from the last incomplete state. Files that already have a `storage_key` cached skip the R2 upload step — only finalize is retried.

**Senior answer:**
IndexedDB is the right persistence layer here because:
- It's available in workers (unlike `localStorage`)
- It can store binary blobs (the compressed file bytes, so we don't recompress on resume)
- It persists across page refreshes and browser restarts

The DB schema has three object stores: `jobs` (one per upload batch), `files` (one per file in the batch), and `blobs` (the compressed binary, keyed by fileId). On resume, the engine checks: if `file.status === 'done'` → skip; if `file.storageKey` is set → skip R2 upload, go straight to finalize; otherwise restart from last incomplete step.

The module-singleton pattern (`workerPool.ts`, `engine.ts`) is critical — these are instantiated once at app boot and survive Vue Router navigation changes. The legacy composables were component-scoped and died on navigation, losing all progress.

**Architect answer:**
One risk with IndexedDB persistence: storage quota. Browsers limit IndexedDB to a percentage of available disk space. We store compressed blobs (not originals) which reduces this risk, but for a 500-photo job at 500 KB each, that's 250 MB of blobs in IndexedDB. We should evict completed job blobs immediately after finalize succeeds, and add a quota check before starting large batches.

**"How would you handle the case where IndexedDB is unavailable (private browsing, storage denied)?"**
> Fall back gracefully to in-memory only — the upload proceeds but without resume capability. The user sees a warning that refresh will restart the upload.
